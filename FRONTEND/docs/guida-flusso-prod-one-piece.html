Procedura ufficiale attuale

Guida step by step per gestire una nuova espansione One Piece con validazione locale e pubblicazione su prod

Questa guida descrive il flusso che oggi e piu sicuro: il set viene prima lavorato in locale, poi pubblicato su prod solo dopo la verifica delle carte e degli slug Card Trader.

Regola base: Supabase Storage resta la source of truth, ma la bozza del nuovo set viene prima testata in locale.

1. Obiettivo del flusso

Quando esce una nuova espansione, il procedimento corretto e:

  1. riallineare prima il locale con lo stato attuale di prod;
  2. scrapare il nuovo set nel Supabase locale;
  3. verificare che le carte siano corrette;
  4. far correggere e validare gli slug Card Trader sul bucket locale;
  5. fare un ulteriore controllo dal pannello admin locale;
  6. pubblicare il risultato da local a prod;
  7. lanciare lo scraper prezzi su prod;
  8. se serve, riallineare di nuovo il locale con prod per avere anche i prezzi aggiornati.

2. Regole da ricordare prima di iniziare

Regola 1

npm run one-piece:scrape e npm run scrape:price leggono l'ambiente attivo da .env.

Regola 2

.env.prod e .env.local sono file di appoggio. Gli script principali non li leggono da soli.

Regola 3

Gli slug Card Trader non vengono auto-generati come URL. Ogni carta riceve solo l'entry del servizio con URL vuoto finche non viene verificato.

Regola 4

Lo scraper prezzi usa solo slug con url presente e verified: true.

Importante: se vuoi pubblicare da local a prod senza fare danni, il locale deve partire da una copia aggiornata di prod. Altrimenti rischi di sovrascrivere prod con uno stato vecchio.

3. File env consigliati

  • .env.prod: credenziali Supabase cloud prod
  • .env.local: credenziali Supabase locale Docker
  • .env: ambiente attivo per gli script principali

Switch pratico

Copy-Item .env.local .env

# quando devi eseguire comandi verso prod
Copy-Item .env.prod .env

Se vuoi essere prudente, fai prima un backup del file attivo:

Copy-Item .env .env.backup

4. Step 0: riallineare il locale con prod prima di iniziare

Obiettivo: partire sempre dall'ultimo stato disponibile in prod, cosi il push finale da local a prod non sovrascrive dati vecchi.

  1. Accendi il Supabase locale Docker.
  2. Lancia il clone da prod a local.
npm run storage:clone-game -- --game=one-piece --source-env-file=.env.prod --target-env-file=.env.local

Dopo questo comando il locale ha:

  • raw set attuali;
  • catalogo attuale;
  • prezzi attuali;
  • immagini attuali.

5. Step 1: scrapare il nuovo set in locale

Obiettivo: costruire il nuovo set sul Supabase locale, non su prod.

  1. Assicurati che .env punti a locale.
  2. Lancia lo scrape del set.
Copy-Item .env.local .env
npm run one-piece:scrape -- --set="NOME SET"

Questo step salva nel Supabase locale:

  • raw set;
  • catalog.min.json aggiornato;
  • immagini webp;
  • entry Card Trader vuota sulle carte.

6. Step 2: verificare che le carte funzionino correttamente in locale

Obiettivo: fare un controllo base prima di entrare nella parte prezzi.

  1. Lascia .env puntato a locale.
  2. Avvia l'app locale.
npm run dev

Controlli consigliati:

  • il set compare nella lista;
  • le carte del set si vedono;
  • le immagini si caricano;
  • non ci sono campi principali palesemente rotti.

7. Step 3: chiedere a Codex di sistemare gli slug sul bucket locale

Obiettivo: correggere e validare gli slug Card Trader prima di toccare prod.

  1. Lascia sempre .env puntato a locale.
  2. Apri Codex nel progetto.
  3. Fai una richiesta esplicita dicendo che deve lavorare sul bucket locale.

Prompt consigliato

Sistema e valida gli slug Card Trader del set "NOME SET" direttamente sul bucket locale.
Non autogenerare URL.
Leggi i dati dal bucket locale, correggi gli slug uno per uno e salva le modifiche in locale.

Prompt per singolo file

Leggi il raw set "NOME_FILE.json" dal bucket locale e correggi gli slug Card Trader delle carte.
Voglio solo URL reali e verificati.
Salva tutto direttamente in locale.
Idea chiave: in questa fase prod non viene ancora toccato.

8. Step 4: controllo finale dal pannello admin locale

Obiettivo: dare un'ultima occhiata umana agli slug prima di pubblicare.

Con .env ancora su locale, usa la pagina:

/admin/set-price-services

Qui puoi:

  • aprire il raw set locale;
  • controllare gli slug carta per carta;
  • correggere manualmente eventuali casi dubbi;
  • verificare che i flag verified siano coerenti.

9. Step 5: pubblicare il risultato da local a prod

Obiettivo: portare su prod il set gia controllato.

  1. Assicurati che il locale sia quello giusto e che il set sia stato verificato.
  2. Lancia il clone da local a prod.
npm run storage:clone-game -- --game=one-piece --source-env-file=.env.local --target-env-file=.env.prod
Attenzione: questo comando copia lo stato del gioco da local a prod. Va usato solo dopo aver fatto prima il riallineamento iniziale prod -> local e dopo aver verificato il nuovo set.

10. Step 6: lanciare lo scraper prezzi su prod

Obiettivo: una volta pubblicato il set con slug gia verificati, aggiornare i prezzi su prod.

  1. Punta .env a prod.
  2. Lancia lo scraper prezzi.
Copy-Item .env.prod .env
npm run scrape:price

Questo step:

  • legge le carte dal bucket prod;
  • usa solo slug Card Trader con URL presente e verified: true;
  • aggiorna i prezzi;
  • riscrive prices.min.json nel bucket prod.

11. Step 7: riallineare di nuovo il locale con prod

Obiettivo: riportare nel locale anche l'ultimo stato prezzi di prod.

  1. Accendi il Supabase locale Docker se non e gia acceso.
  2. Lancia di nuovo il clone da prod a local.
npm run storage:clone-game -- --game=one-piece --source-env-file=.env.prod --target-env-file=.env.local

Questo passaggio non e obbligatorio se ti basta sapere che prod e aggiornato, ma e consigliato se vuoi continuare a lavorare in locale con tutto allineato.

12. Step 8: tornare al lavoro locale normale

Copy-Item .env.local .env
npm run dev

Controlli finali consigliati:

  • lista carte;
  • immagini;
  • prezzi;
  • pagina admin slug;
  • endpoint tipo /api/games/one-piece/meta.

13. Checklist rapida

  1. Clone iniziale prod -> local.
  2. .env su locale.
  3. Scrape nuovo set in locale.
  4. Controllo carte in locale.
  5. Chiedi a Codex di sistemare gli slug sul bucket locale.
  6. Controllo finale nel pannello admin locale.
  7. Clone local -> prod.
  8. .env su prod.
  9. Scrape prezzi su prod.
  10. Clone finale prod -> local.

14. Cose da non fare

  • Non scrivere subito il nuovo set direttamente su prod se prima vuoi controllarlo con calma.
  • Non pubblicare local -> prod senza aver prima riallineato il locale con prod.
  • Non lanciare lo scraper prezzi prima di aver sistemato gli slug.
  • Non considerare i vecchi JSON del repo come verita del dato.
  • Non usare il dashboard Storage per migrare a mano file e cartelle se puoi evitarlo.

15. Riassunto in una frase

Prod viene alimentato solo dopo che il nuovo set e stato scrappato, controllato e validato in locale.
